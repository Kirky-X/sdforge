# ⚡ Sdforge Performance Baselines

> Baseline recorded 2026-09-11 (routing/JSON); TLS group: 2026-09-29; simd-json / middleware tiers: 2026-09-30
> Environment: WSL2 (linux 6.6.87) x64 · Rust 1.97.1 · release profile (`lto=fat`, `codegen-units=1`, the repo's existing configuration)
> criterion reports a median interval [low, median, high]; the tables below take the median.

Reproduction commands:

```bash
cargo bench --bench runtime_bench --features http
cargo bench --bench runtime_bench --features serve-tls -- "tls_termination|plaintext_baseline|tls_cert_reloader"
cargo bench --bench runtime_bench --features http,grpc,streaming -- "grpc_stream"
cargo bench --bench runtime_bench --features http,simd-json -- "simd_json"
cargo bench --bench runtime_bench --features http,security,etag,metrics,context,idempotency -- "middleware_tiers"
```

> The local baseline numbers serve as a regression reference (the CI threshold gate awaits stable multi-machine sampling before being enabled). Compile-time costs (macro expansion, dependency compilation) are recorded separately in the [compile-time gating benchmarks](VS_SERVER_LESS.md) and are not part of the runtime baselines.

## 🔀 Request Hot Path (Route Dispatch)

`route_dispatch/*` calls `Service::call` directly on the `http::build()` output, covering axum route matching plus the extraction/serialization closures generated by `#[forge]` (`plain_get` / `path_param_get` latency and throughput in the [baseline summary](#-baseline-summary)). The extra cost of path-parameter extraction is about **+50 ns/request** (about +9%).

## 🔐 TLS Termination Hot Path (`serve-tls`)

`tls_termination/*` / `plaintext_baseline/*` / `tls_cert_reloader/*` run over real loopback TCP (`serve_with_graceful_shutdown_tls` vs `serve_with_graceful_shutdown`, same router and same drain configuration, transport layer only differs):

- **Pooled connections**: request round trip after TLS record-layer encryption/decryption is ~35 µs, same order of magnitude as plaintext ~45 µs (within loopback noise) — the sustained cost on keep-alive connections is negligible.
- **New connections**: the entry cost including a full TLS 1.3 handshake is ~559 µs (about 16× the pooled path), dominated by asymmetric handshake operations and round trips; size capacity for short-connection high-churn deployments accordingly.
- **Certificate hot reload**: the `resolve` read path costs ~48 ns per call (resolved once per handshake; no `RwLock` read degradation); a single `reload` costs ~26 µs (file IO + PEM parsing + key assembly; use `reload_async` on tokio workers); a batch of one disk swap overlapped with 4 concurrent handshakes costs ~3.26 ms — reloads and entry traffic never block each other.
- `resolve_read_path` uses `end_entity_certificate()` as the proxy metric (rustls `ClientHello` cannot be constructed inside the bench; both are lock reads + end-entity DER access).

## 🌊 gRPC Server-Streaming (`grpc` + `streaming`)

`grpc_stream/*` calls `SdForgeGrpcService::call_stream` directly (no network; focuses on dispatch + mapping overhead):

- **Linear increments**: 10 items ~7.3 µs → 1000 items ~352 µs, roughly ~350 ns per incremental item (guard-chain floor + per-item mapping).
- **Per-item mapping**: `stream_output_from` consumes 1e4 items in ~1.52 ms (~152 ns/item, `to_value` + `extract_value` two phases).
- Recorded 2026-09-30 (same day as the i18n group).

## 🌐 i18n Translation Lookup

`i18n_translation/*`: `translate_or_fallback` is a control-plane path (MCP tool listing / CLI help / OpenAPI per-route / gRPC GetInfo), not a request hot path. Fallback ~45 ns, full-table (1e4 host registrations) hit ~70 ns — lock overhead is linear, and OpenAPI generation for thousand-scale routes (2 critical sections per route) totals microseconds, with no regression risk. Recorded 2026-09-30.

## ⚙️ Middleware Stack Tiers (`build_with_config_ext`)

`middleware_tiers/*` calls the Router produced by `build_with_config_ext` directly (`Service::call` GET `/api/v1/bench/ping`, full middleware chain). Reproduction command and feature set: `cargo bench --bench runtime_bench --features http,security,etag,metrics,context,idempotency -- "middleware_tiers"` (t1/t6 need security, t2 needs etag, t3 needs metrics, t4 needs context, t6 needs idempotency; cors is a pure-config tier, not a feature). The table below is one full 2026-09-30 run; same-machine batch variance is roughly **±10%** (rerun comparison measured t1 213→204 µs, t0 8.6→5.2 µs — different harness scopes, see below); small drift in table values after reruns is normal:

| Tier | Stacked item | Increment over T0 |
|------|--------|--------------|
| t0_base | Always-on layers: RequestBodyLimit + Compression + Timeout + security response headers | floor ~5.2 µs |
| t1_auth | + ApiKey auth (valid key) | **+198 µs** (dominated by the fixed latency of ApiKey constant-time verification — an explicit security-for-performance trade-off) |
| t2_etag | + ETag conditional requests | ~noise (−0.3 µs, same order as the floor) |
| t3_metrics | + metrics middleware | ~noise (−0.3 µs) |
| t4_context | + context (request_id/trace_id) | +0.1 µs |
| t5_cors | + CORS | +1.6 µs |
| t6_all | t1+etag+metrics+context+cors+idempotency(enabled) | ~221 µs (auth constant-time latency dominates; other increments are swamped) |

**Scope and disclaimers**: ① direct `Service::call` (no network/transport layer), so the increments reflect the middleware chain itself; the tokio runtime is hoisted outside the group (each iteration only `block_on`, no build constant); ② the ~200 µs magnitude of t1/t6 comes from ApiKey constant-time verification latency (a fixed sleep against timing attacks), not a per-layer linear sum — JWT/OAuth2 tiers were not measured (same constant-time source; magnitude reference t1); ③ HTTP-side rate limiting is mounted by the caller via `rate_limit_layer` (outside the `build_with_config_ext` assembly surface; rate limiting is assembled via `build_with_config_ext_rate_limited`), so it has no tier; ④ the idempotency tier measures GET pass-through overhead (write requests carrying `Idempotency-Key` incur additional cache-write cost, not covered); ⑤ single-machine data (WSL2), for regression reference only, not an absolute capacity promise.

## 📦 JSON Serialization and simd-json Comparison

Corresponds to baselines `serialize_nested_object` / `deserialize_nested_object` (7-field nested object, see the [baseline summary](#-baseline-summary)).

`simd_json/*` (measured 2026-09-30, `simd-json` feature) uses the `core::json` facade scope (`simd_to_string` / `simd_from_str`, i.e. the simd-json serde compatibility layer; `from_str` includes input byte copying):

- **Small payloads (~200 B)**: serialization simd ~185 ns vs serde ~147 ns; deserialization simd ~1.13 µs vs serde ~444 ns — simd is slower across the board (the serde compatibility bridge plus SIMD startup/allocation costs dominate).
- **Large payloads (~64 KiB / 512 items)**: deserialization simd ~198 µs vs serde ~160 µs — still no gain.
- **Conclusion and disclaimer**: in this environment (WSL2, simd-json 0.18 `serde_impl` mode, target type `serde_json::Value`), the facade path shows **no speedup** from simd-json in practice; its public gains lie mainly in direct DOM parsing (`simd_json::to_owned_value`) and larger payloads, both outside the facade's coverage. Whether to enable `simd-json` should not be decided based on the expected speedup in this table; the measured numbers are for decision reference only.
