# 📖 Sdforge User Guide

This guide targets SDForge users and covers the full path from installation, core concepts, and configuration to advanced usage. SDForge is a Rust-based declarative SDK framework: through the `#[forge]` proc macro it automatically generates multi-protocol service interfaces (HTTP + MCP + gRPC + WebSocket + CLI) from unified function annotations, and performs compile-time protocol selection via Cargo features — disabled protocols produce zero compiled code.

## 🧭 Introduction

SDForge's core idea: **one function annotation, many protocol consumers**. You only describe the endpoint with the `#[forge]` macro (name, version, path, method, etc.), and the framework generates the registration code for the corresponding protocols at compile time:

- Enable `http` → Axum routes
- Enable `mcp` → MCP tools (official rmcp SDK, 2026-07-28 spec)
- Enable `grpc` → tonic gRPC methods
- Enable `cli` → clap commands
- Enable `openapi` → OpenAPI 3.1 spec entries

Disabled protocols never enter the build artifact at all — the fundamental difference between SDForge and "full-bundle" frameworks (quantified comparison in the [compile-time gating benchmarks](VS_SERVER_LESS.md)).

## 🚀 Quick Start

### Installation

```bash
cargo add sdforge
```

For the pinned-version `Cargo.toml` form and the note that "`default = []` requires enabling protocol features explicitly on demand", see [README · Quick Start](../../README.md#-quick-start).

### Define your first API

```rust
use sdforge::prelude::*;

#[forge(
    name = "get_user",
    version = "v1",
    path = "/users/:id",
    method = "GET",
    description = "Get a user by ID"
)]
async fn get_user(id: u64) -> Result<serde_json::Value, ApiError> {
    Ok(serde_json::json!({ "id": id, "name": "Test" }))
}

#[tokio::main]
async fn main() {
    sdforge::init_all_plugins(); // consolidate inventory registrations so the linker doesn't strip them
    let app = sdforge::http::build();
    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000").await.unwrap();
    sdforge::axum::serve(listener, app).await.unwrap();
}
```

Once running, `GET /api/v1/users/42` is available (the version is automatically joined into the path prefix `/api/{version}`). `sdforge::axum` in the example is the framework's forwarded axum facade, so downstream crates do not need to depend on axum directly.

## 🧩 Core Concepts

### The `#[forge]` macro

`#[forge]` requires `name` and `version`; for the complete list, semantics, and defaults of the basic parameters (`path` / `method` / `status` / `description`, etc.) and the advanced parameters and bare flags (`i18n_key` / `cache_ttl` / `ws_path` / `stream` / `no_prefix` / `validate` / `paginate` / `on_start` / `on_stop` / `auth(role = "...")`), see the "`#[forge]` parameters" section of the [API reference](API_REFERENCE.md#forge-parameters).

### Version routing

The `version` parameter determines the path prefix: `/api/{version}/...`. Multiple versions of the same `name` can coexist, each mapped to its own function and response type.

### Module prefix

`#[service_module(prefix = "/auth")]` adds a unified prefix to all endpoints in the module, producing paths like `/auth/api/v1/login`.

### Path parameters

Segments of the form `:id` in the path map automatically to same-named function parameters, with multi-level nesting supported (e.g. `/posts/:post_id/comments/:comment_id`).

### Unified registration (inventory)

The registration information generated by `#[forge]` is submitted at compile time via `inventory::submit!()`. The application must call `sdforge::init_all_plugins()` once at startup to prevent the linker from optimizing the registrations away; it returns `PluginCounts`, usable to confirm per-protocol registration counts.

### The unified handler contract

Handlers for all protocols follow the `fn(HandlerArgs, HandlerState) -> HandlerFuture` contract: `HandlerArgs` is constructed automatically from clap / tonic / axum extractors, and application state is injected via `downcast_state::<T>()` (declared in the handler with an `#[state] db: Arc<Db>` parameter).

## ⚙️ Configuration

### Configuration types

The configuration module (`sdforge::config`, requires the `http` feature) provides `SdForgeConfig` / `ServerConfig` / `ApiConfig` / `AuthConfig` / `CorsConfig` / `TlsConfig` / `TracingConfig` / `CacheConfig` / `SecurityConfig` / `EnvHelper` / `ConfigError` and more; for each type's purpose and defaults see the configuration module section of the [API reference](API_REFERENCE.md#-configurationextension-api).

### Building with configuration

```rust
use sdforge::config::SdForgeConfig;
use sdforge::http::build_with_config_ext;
use axum::Router;

let config = SdForgeConfig::default();
// The application's own routes must be merged in first, then the middleware stack layered
let app = build_with_config_ext(Router::new(), &config)?;
```

> **Application routes must be merged in via `build_with_config_ext`**: axum's `Router::layer` only affects
> routes registered before it is called. sdforge provides no "stack-first, merge-later" assembly entry point —
> `merge`-ing application routes into a Router that already has the middleware stack layered lets those routes
> bypass the entire middleware stack (no auth, no rate limiting, no security headers), effectively exposing
> a set of unauthenticated endpoints.

> **Probe path ownership**: the built-in probes (`/healthz`, `/readyz`) and the `/metrics` endpoint are
> auto-mounted when the `health` / `metrics` features are on. The pre-mount occupancy check covers both
> sources — inventory-registered routes and same-named paths declared by the caller's `base`: a same-named path
> is taken over by the caller, the built-in mount skips and warns (occupancy is determined via "trial
> registration"; axum provides no route enumeration API), and there is no more build-time panic. When `base`
> needs to manage probes itself it can simply declare the same-named path, and the built-in probe yields.

### TOML configuration file

SDForge uses a self-contained TOML configuration (no external config center required). Example configurations live in the repository's `examples/config/` (full list in the [examples](#-examples) section of this guide).

Rate-limiting and cache configuration example:

```toml
# config.toml
# The value is limiteron's FlowControlConfig (version + rule list), not a single threshold field
[security.rate_limit]
version = "1.0"

[security.rate_limit.global]
storage = "memory"   # memory | postgresql | redis
cache = "memory"     # memory | redis | none
metrics = "prometheus"  # prometheus | statsd | none

[[security.rate_limit.rules]]
id = "http_default"
name = "HTTP default rate limit"
priority = 100

[[security.rate_limit.rules.matchers]]
type = "User"
user_ids = ["*"]

[[security.rate_limit.rules.limiters]]
type = "TokenBucket"
capacity = 60        # bucket capacity (burst ceiling)
refill_rate = 1      # refill per second

[security.rate_limit.rules.action]
on_exceed = "reject"

[cache]
enabled = true
default_ttl_secs = 600
max_items = 5000
track_stats = true
```

> **Rate-limiting assembly point**: the assembly entry points are unified on the ext series of "merge routes first, then stack" — axum's
> `Router::layer` only affects routes registered before the call; routes merged after the stack bypass
> the entire middleware stack, so no "stack-first" entry point exists. The `security.rate_limit` rate limiter is
> constructed asynchronously by limiteron and cannot be installed through a synchronous entry point: to make rate limiting
> actually effective, use `http::build_with_config_ext_rate_limited(base, &config).await?`;
> it installs the rate-limiting layer outside the auth layer (unauthenticated floods get rate-limited first),
> while probes and `/metrics` are unaffected.
>
> ```rust
> let router = sdforge::http::build_with_config_ext_rate_limited(base, &config).await?;
> ```
>
> **Framework-provided routes only, no rate limiting**: use the synchronous entry point `http::build_with_config_ext(Router::new(), &config)?`.
> The two needs (merging routes / installing rate limiting) used to be mutually exclusive (the merge-routes entry
> installed no rate limiting; the rate-limiting entry accepted no caller routes); the ext series now unifies them.
>
> ```rust
> let router = sdforge::http::build_with_config_ext_rate_limited(app_routes, &config).await?;
> ```

## 🔧 Advanced Usage

### Parameter validation and struct query parameters (`validate` × `#[param]`)

Handler parameters declare their extraction source and rules via `#[param(...)]`; `kind` takes `path` / `query` / `header` / `form` / `body` / `state` / `extension` (the `#[state]` attribute is equivalent to `kind = "state"`), and rules include `ge` / `le` / `min_length` / `max_length` / `not_blank` / `email`; rules take effect only when the endpoint carries the `#[forge(validate)]` flag, and violations return 422 with field-level errors.

`serde_urlencoded` only supports flat `key=value`, so struct-typed query parameters extracted through the envelope by default fail nested deserialization and return 400. To receive a struct via flat query parameters, explicitly opt in with `flatten`:

```rust
#[derive(Debug, serde::Deserialize)]
struct SearchFilters {
    budget: u64,
    keyword: String,
}

#[forge(name = "search", version = "v1", path = "/search", method = "GET", validate)]
async fn search(
    #[param(kind = "query", ge = 1)] page: u64,
    #[param(kind = "query", flatten)] filters: SearchFilters,
) -> Result<serde_json::Value, ApiError> {
    // GET /api/v1/search?page=1&budget=50&keyword=hello
    Ok(serde_json::json!({ "page": page, "budget": filters.budget, "keyword": filters.keyword }))
}
```

`flatten`'s four constraints fail loud at macro expansion: mutually exclusive with validation rules (field validation belongs to the flattened struct itself), only valid for `kind = "query"`, accepts only boolean literals (`flatten` / `flatten = true` / `flatten = false`), and multiple can coexist in the same signature without conflicting with envelope-extracted scalar parameters. For the full attribute table and semantics see [API reference · `#[param]` parameter attributes](API_REFERENCE.md#param-parameter-attributes).

### gRPC services

With the `grpc` feature enabled, `#[forge(grpc_method = "...")]` registers the handler via inventory, and `SdForgeGrpcService` routes by `grpc_method` (implementing `Call` / `GetInfo`, plus server-streaming `CallStream` — which requires `streaming`; it returns unimplemented when `streaming` is off). Start the server via `build_server_with_config`:

```rust
use sdforge::grpc::{GrpcServerConfig, build_server_with_config};
use sdforge::prelude::*;
use sdforge::forge;

#[forge(
    name = "grpc_echo",
    version = "v1",
    grpc_method = "comprehensive.echo",
    description = "gRPC echo handler"
)]
async fn echo(msg: String) -> Result<serde_json::Value, ApiError> {
    Ok(serde_json::json!({ "echo": msg }))
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    sdforge::init_all_plugins();
    let config = GrpcServerConfig::default();
    // When the security feature is on, require_auth defaults to true:
    // without auth configured the server refuses to start (fail-safe); dev environments may set false explicitly
    build_server_with_config("0.0.0.0:50051", config).await?;
    Ok(())
}
```

Return values must satisfy `serde::Serialize`, the error type must be `ApiError`, and the argument payload cap is 1 MiB. Application state is injected via `GrpcServerConfig.state` (`Arc<dyn Any + Send + Sync>`).

> **⚠️ Do not use `build_server(addr)`**: that entry point is deprecated (marked `#[deprecated]` in source); it starts an **unauthenticated** server and cannot configure authentication. Always use `build_server_with_config`.

#### gRPC graceful shutdown (`build_server_with_graceful_shutdown`)

The assembly chain is identical to `build_server_with_config` (auth interceptor, connection cap/timeout/keepalive, TLS, `extra_services`), ending with tonic `serve_with_shutdown`: once the `signal` future completes it stops accepting new connections, waits for in-flight requests to finish, and returns `Ok(())` (semantics aligned with HTTP-side axum `with_graceful_shutdown`: governed by future completion — a never-completing future stays resident forever):

```rust
use sdforge::grpc::{GrpcServerConfig, build_server_with_graceful_shutdown};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    sdforge::init_all_plugins();
    let config = GrpcServerConfig::default();
    build_server_with_graceful_shutdown("0.0.0.0:50051", config, async {
        tokio::signal::ctrl_c().await.ok();
    })
    .await?;
    Ok(())
}
```

#### Service parameters

| Field | Type | Default | Description |
|------|------|--------|------|
| `max_connections` | `usize` | 1000 | Concurrent connection cap |
| `timeout_seconds` | `u64` | 30 | Per-request timeout (seconds); 0 is a legal value (covered by integration tests) |
| `http2_keepalive_interval` / `http2_keepalive_timeout` | `Option<Duration>` | `None` | HTTP/2 keepalive probe interval and timeout (`None` = tonic defaults) |
| `require_auth` | `bool` | `true` | When `true` and `auth` is `None`, assembly refuses to start |
| `auth` | `Option<BearerAuth>` (`security`) / `Option<()>` | `None` | JWT verification credential; unavailable when `security` is not enabled |
| `rate_limiter` | rate-limiter injection | - | Server-side rate limiting (`ratelimit`) |
| `extra_services` | `Vec<ExtraServiceMount>` | empty | Same-port mounting of the app's own tonic services (`Clone` shares the same callback list) |
| `tls` | `Option<tonic::transport::ServerTlsConfig>` (`grpc-tls`) | `None` | Wiring only, no certificate loading/rotation |
| `idempotency_store` / `idempotency_ttl_secs` / `idempotency_inflight_ttl_secs` | (`idempotency`) | `None` / 86400 / 30 | Idempotent replay-protection store, replay window, and in-flight claim cap |

#### gRPC server-streaming (`streaming` × `grpc`)

`#[forge(grpc_method, stream = true)]` (plus the `streaming` feature) declares a streaming endpoint: the handler returns `StreamResponse<T>`, sent item by item as `CallResponse` over the `CallStream` RPC — each item success:true + JSON data; streaming endpoints come with the rate-limit/auth/RBAC/payload-cap guard chain (both `Call` and `CallStream` RPCs put rate limiting **outermost** — unauthenticated floods never enter the constant-time-verified OS thread sleep, aligning with the HTTP stack's "rate limiting outside auth" order); item-level errors are delivered as success:false messages and the stream continues (aligned with SSE error event semantics). The unary and streaming registries are mutually exclusive: `Call` hitting a streaming method or `CallStream` hitting a unary method both return `failed_precondition` with direction guidance; the streaming path does not support idempotent replay (carrying `idempotency-key` is explicitly rejected).

Two streaming lifecycle boundaries: ① the `context` feature's request_id/trace_id scope covers the handler body (from argument assembly to returning `StreamResponse`) but does not cross into the subsequent stream production phase (that phase is polled by the tonic connection task, and producer tasks the user spawns themselves do not inherit task_local) — when per-item logs need correlation ids, carry them explicitly inside the producer task; ② a producer task panic/abort → the sender drops → the stream ends with **normal exhaustion**, so the client cannot distinguish a complete stream from a truncated one — callers needing fail-visible behavior should hold the JoinHandle, watch it, and inject an item-level error on abnormal exit (an `Err(msg)` item → success:false, stream continues). Client disconnection is defined as cancellation semantics: the sender's `send` returns Err, and the producer loop should exit.

```rust
use sdforge::streaming::create_stream_channel;
use sdforge::forge;

#[forge(
    name = "count_stream",
    version = "v1",
    grpc_method = "examples.count_stream",
    stream = true
)]
async fn count_stream(count: Option<u64>) -> Result<sdforge::streaming::StreamResponse<String>, sdforge::core::ApiError> {
    let (tx, response) = create_stream_channel::<String>(8);
    tokio::spawn(async move {
        for i in 0..count.unwrap_or(3) {
            if tx.send(Ok(format!("evt-{i}"))).await.is_err() {
                break; // client disconnected → stop producing
            }
        }
    });
    Ok(response)
}
```

With `grpc` on and `streaming` off, a `stream = true` declaration is a compile-time error (fail-loud; the method never silently disappears); `CallStream` returns `unimplemented` on servers without `streaming`.

#### Custom tonic service mounting (`extra_services`)

The application's own proto services (e.g. `XxxServer<T>` generated from consumer-built protos) can coexist on the same port as `SdForgeService` without another process: `GrpcServerConfig.extra_services` accepts a set of `Arc<dyn Fn(&mut tonic::service::RoutesBuilder) + Send + Sync>` callbacks; at assembly time each callback gets `add_service(...)` registering any tonic service implementing `NamedService`, then the server is mounted uniformly (`SdForgeService` registered last):

```rust
use sdforge::grpc::{GrpcServerConfig, build_server_with_config};

let nexusflow_svc = /* the service implementation of NexusFlow's own proto */;
let mut config = GrpcServerConfig::default();
config.require_auth = false; // or configure auth (see below)
config.extra_services.push(std::sync::Arc::new(move |routes| {
    routes.add_service(nexusflow_v1::NexusFlowServer::new(nexusflow_svc.clone()));
}));
build_server_with_config("0.0.0.0:50051", config).await?;
```

Semantic boundaries: mounted services share server-level configuration (connection cap, timeout, keepalive, TLS) and, under the `security` feature, the global JWT authentication interceptor (requests without credentials are rejected before ever reaching the custom service); `auth_verifier` (`GrpcAuthVerifier`) is `SdForgeService`'s per-call verification and does **not** apply to custom services — applications needing equivalent authentication must implement it inside their own services. The route shape is `/{S::NAME}/*rest` (tonic axum routes): a custom service's NAME must not conflict with `sdforge.v1.SdForgeService`; a conflict panics at assembly time (fail-loud), with no silent renaming. Cloning `GrpcServerConfig` shares the same callback list (`Fn` not `FnOnce`; the closure captures the service in an `Arc` and clones it for construction).

### HTTP TLS termination

With the `serve-tls` feature enabled, `http::tls` terminates TLS in-process with rustls (aws-lc-rs provider): cert/key load from the PEM files pointed to by `TlsConfig` (key files readable by group/other emit a warn on unix; `chmod 600` recommended), ALPN is configurable (default `["h2", "http/1.1"]`), and every request gets `ConnectInfo<SocketAddr>` injected automatically (TLS terminates in-process with no fronting proxy, so rate limiting/auditing get an unspoofable client IP). Shutdown choreography reuses graceful's three phases (stop accepting → drain in-flight → stop hooks), and `TlsServeConfig` adds three pre-auth guardrails — handshake timeout (default 10s), HTTP/1.1 header-read timeout (default 30s, h1 only), and HTTP/2 keep-alive probing (default 30s interval / 20s confirm timeout; h2 connections stalling without frames after handshake are cut on timeout, tunable or disableable via `with_http2_keepalive`):

```rust
use sdforge::config::TlsConfig;
use sdforge::http::tls::{TlsServeConfig, serve_with_graceful_shutdown_tls, tls_acceptor};
use sdforge::http::{default_shutdown_signal, GracefulShutdownConfig};

let tls = TlsConfig::new("cert.pem", "key.pem");
let acceptor = tls_acceptor(&tls)?;
let listener = tokio::net::TcpListener::bind("0.0.0.0:8443").await?;
let config = TlsServeConfig::default()
    .with_graceful(GracefulShutdownConfig::default());
serve_with_graceful_shutdown_tls(
    app,
    listener,
    acceptor,
    default_shutdown_signal(),
    config,
).await?;
```

For certificate rotation use `ReloadingTls`: acceptor and reloader are bound at compile time (eliminating the broken shape of "config and reloader split apart, hot reload silently dead"); after swapping the certificate on disk call `reload()` — note it is a blocking operation (file IO + PEM parsing); a timer thread may call it directly, but on tokio workers use `reload_async()`. When the reloaded key pair does not match the certificate, the old certificate is kept and an error returned, without interrupting the live service. `TlsConfig` can also be written into the configuration file (`server.tls`; `SdForgeConfig::validate()` validates non-empty paths and ALPN legality). The gRPC-side counterpart is `GrpcServerConfig::tls` (the `grpc-tls` feature, tonic `ServerTlsConfig` wiring) — the two are doc-cross-linked but implemented independently.

### CLI applications

With the `cli` feature enabled, `#[forge(cli = true)]` registers commands; `CliBuilder::execute()` handles build/parse/dispatch/output/exit in one stop. For the minimal runnable example see [README quick start](../../README.md#-minimal-runnable-example) (source `examples/basic_cli.rs`).

A returned `Value::String` prints the raw string (no quotes); other types print JSON. `CliBuilder` also supports `with_dependencies()` (inject state), `with_name()` (program name), and `with_global_arg()` (global arguments).

### MCP integration

- **Stateless protocol**: `StatelessServerHandler` implements `rmcp::ServerHandler`; the HTTP header protocol is parsed by `parse_mcp_headers` from `Mcp-Method` / `Mcp-Name` (missing headers return `McpHeaderError`; the HTTP status mapping is up to the downstream transport adapter layer, e.g. mapped to 400)
- **stdio service**: `mcp::serve_stdio()` wraps `rmcp::ServiceExt` + stdio transport
- **State & identity wiring**: `SdForgeMcpServer::with_state(...)` injects application state and `SdForgeTool::call_with_ctx` receives a `ToolCallContext` (state via `downcast_state`, verified identity via `ctx.user_id()` under `security`); `#[state]` endpoints with `tool_name` dispatch for real once `with_state` is wired (fail-explicit `forge.state_missing` otherwise)
- **Streamable HTTP mounting**: enable `mcp-http` and mount rmcp's `StreamableHttpService` at `/mcp` with `sdforge::axum` — all types resolve through the `sdforge::rmcp` re-export (no direct rmcp dependency; included in `full`). For public deployment configure origin validation in `StreamableHttpServerConfig` (default `allowed_origins` is empty = validation off; `allowed_hosts` defaults to loopback only)
- **MRTR multi round-trip**: `MrtrSessionManager` manages sessions; tools suspend via `InputRequiredResult` awaiting supplementary input, auto-cancelled after a 300-second timeout
- **Cache semantics**: the `cache_semantics` module handles `ttlMs` / `cacheScope` (`global` / `request`)

For the migration example see `examples/src/mcp/migration_2026.rs`.

### OpenAPI documentation

With the `openapi` feature enabled, `#[forge]` automatically registers `OpenApiRouteInfo`; for usage examples of `generate_openapi_spec()` and `OpenApiBuilder` see the [API reference](API_REFERENCE.md#openapi-generation).

Enabling the `docs` feature further provides the Swagger UI (`swagger_ui_router()`, requires `http`) and CLI/MCP Markdown documentation output (`generate_docs` / `write_docs`).

### SSE streaming and WebSocket

- **SSE** (`streaming` feature): `StreamEvent` / `StreamResponse` / `stream_to_sse` / `create_stream_channel`. The stream has a built-in idle heartbeat: while the source is silent, a `: keep-alive` comment frame is sent every 10s (ignored by clients) to prevent intermediaries from cutting idle connections; data frames reset the heartbeat timer, and a source silent for 30s still terminates with an error event + `complete`
- **WebSocket** (`websocket` feature, requires `http` + `streaming`): `websocket_upgrade`, `WebSocketHandler`, `ConnectionManager`, `WebSocketConfig`; `#[forge(ws_path = "...")]` declares the mount path (consumed by `websocket::build()`), defaulting to `/{name}` when undeclared
- **WebSocket assembly**: `websocket::build()` assembles with default configuration (handshake does not verify credentials); `websocket::build_with_config(config)` injects a custom `WebSocketConfig` whose `auth` (JWT) / `api_key_auth` (API key) verify credentials before upgrade, returning 401 for missing or invalid credentials. `WebSocketConfig::max_message_size` (default 1 MiB) is the message size cap: text frames over the cap disconnect directly; `parse_websocket_message_with_limit(text, limit)` parses a message against a given cap

### Caching

With the `cache` feature enabled, oxcache is passed through directly: `SyncCache` / `SharedCache` / `DashMapCache` (the `OxcacheSyncCache` alias), supporting key normalization, pattern invalidation (`invalidate(pattern)`), batch deletion (`delete_many`), and statistics (`get_stats`). On the HTTP side there is additionally the `ResponseCacheLayer` response-caching middleware (needs `cache` + `http`), which caches successful responses of GET routes automatically.

### Internationalization and logging

- **i18n**: the translation registry (`register_translation` / `set_locale` / `translate_or_fallback`) is always available; the `i18n` feature additionally provides ICU4X's `HttpI18nFormatter` (locale-aware number/date/plural formatting and Accept-Language parsing). HTTP error bodies pick their language from the request's `Accept-Language` (the request-scoped locale of `build_with_config_ext` + the unified 404 error body for unmatched routes + per-request localization of rate-limit rejection bodies), with the process locale only as fallback
- **Logging**: the `inklog` feature bridges bare `log` calls into inklog's `LoggerManager` structured pipeline (`init_inklog_logger()`; since 0.5.0-rc it has absorbed the removed in-house `StructuredLogger` stack and is the single entry point for structured logging, with real rotation), and enables the `#[forge::log]` declarative logging attribute macro (enter/exit/duration/error + DataMasker masking; using the macro with the feature off is a loud compile-time error)
- **`#[forge::log]` boundaries and semantics**: the `unsafe` qualifier of an `unsafe fn` propagates verbatim to the shell function (callers still need an unsafe block to fulfill the safety contract; the macro does not wrap an unsafe fn into a safe one); the shell does not catch panics/task cancellation — when the function body panics or the async task is cancelled, no `fn_exit` record is produced (callers needing failure visibility should catch explicitly inside the function body, or watch the JoinHandle at the call site); **methods inside trait impls are not supported** (the macro appends a hidden inner function in the same impl block, and trait impls allow no extra members); `const`/variadic are rejected fail-loud at expansion. Lazy payload rendering: when the target log level is filtered by the global max_level, argument capture and mask rendering do not run (with an info production config, debug logs entering the log cost zero extra allocations); payloads over 64 KiB are truncated before masking (inklog DataMasker skips masking entirely for >1 MiB input, and the shell-level truncation guarantees sensitive values never enter logs in plaintext); the credential key-value rules also cover quoted-key forms (`"password":"hunter2"` and `password=hunter2` are masked alike) <!-- pragma: allowlist secret -->

### Client SDK generation

With the `sdk` feature enabled, client artifacts are generated from the registered routes via the retained CLI subcommand:

```bash
myapp sdk --lang all --output-dir ./sdks --reqwest
# → sdks/sdforge_client.rs   (zero-external-dependency Rust client; --reqwest adds the reqwest transport)
# → sdks/sdforge_client.ts   (fetch + embedded type definitions)
```

The Rust artifact abstracts transport behind a `Transport` trait (implement it once to plug in any HTTP stack),
returns raw JSON strings, and leaves deserialization to the consumer's own models; `base_url` is joined into
the full URL by the client's `call` before being handed to `Transport::execute` (trailing slashes stripped
automatically, so the transport receives the full URL and no longer needs to join the base itself); the
`--reqwest` section is gated by `#[cfg(feature = "reqwest")]` inside the generated
file, and consumers must declare the `reqwest` dependency themselves. Method names are derived before rendering
sorted by `(method, path)`, so artifacts are independent of route registration order
(deterministic snapshot locking). Comment text in artifacts is rendered via `sdforge::i18n`'s built-in
catalog by active locale (English by default; the `SDFORGE_LANG` detection chain can switch it), while comment
markers (`//!` / `///` / `/** */`) and the code skeleton do not change with language. Libraries may also call
`sdforge::sdk::generate_rust_client / generate_typescript_client` directly for customized
generation.

### Distributed rate limiting and Redis L2 cache (multi-replica deployment)

For multi-replica deployments enable `ratelimit-dist` (distributed rate limiting) and `cache-l2` (cross-replica L2 cache):

```rust,ignore
// Distributed rate limiting: replicas share the RedisDistributedLimiter counting backend (atomic Lua window);
// quotas are globally consistent across replicas; use InMemoryDistributedLimiter for single instance/tests.
let backend = Arc::new(limiteron::limiters::RedisDistributedLimiter::new(cache, 100, 60_000));
let limiter = DistributedRateLimiter::new(backend, DistributedRateLimitConfig::new(100, Duration::from_secs(60)));

// L2 cache: cross-replica shared cache layer (L1 in-process cache in front)
let l2 = RedisL2Cache::connect(&RedisL2CacheConfig::new(redis_url).with_default_ttl(Duration::from_secs(300))).await?;
```

**Redis production configuration guidance (AUTH + TLS)**:

- **Authentication (AUTH/ACL)**: carry credentials in the connection string `redis://default:<AUTH>@host:6379/0`;
  inject credentials only via environment variables or secret management — never write them into code/config
  repositories. Enable Redis 6+ ACL to bound the application account's permissions (get/set/del/eval on the
  target db only).
- **TLS**: for cross-segment/public-internet deployments use `rediss://host:6379` (TLS transport encryption);
  in high-trust intranet environments `redis://` with network isolation (VPC/security groups) as compensation is
  acceptable, and the compensating measures must be recorded in the deployment review.
- **Key prefix**: when multiple apps share an instance, mutually distinct `key_prefix` settings are mandatory
  (rate limiting `with_key_prefix` / L2 `with_key_prefix`) to prevent key collisions and cross-app unauthorized enumeration.

**Backend-unreachable behavior (explicitly configurable)**:

| Component | Policy | Default | Rationale |
|------|------|------|------|
| Distributed rate limiting | fail-open (allow + 60s throttled warning) + adapter-layer circuit breaker (5 consecutive backend errors open the circuit; while open, requests are decided without hitting the backend; half-open probing recovers after 30s; `with_circuit_failure_threshold` / `with_circuit_open_duration` tunable) | fail-open | Rate limiting is a protective mechanism, not a correctness mechanism: fail-close on counting-store failure would amplify a storage failure into full-service unavailability, violating availability-first. The circuit breaker covers the black-hole shape — while the backend neither errors nor responds until timeout, requests no longer pay the full timeout each time. Deployments needing hard security semantics (anti-brute-force/anti-credential-stuffing) switch to `BackendFailurePolicy::FailClose` explicitly (while the circuit is open, rejections use `CircuitBreakerError`, never silently allowed) |
| Redis L2 cache | inherently fail-open (read failure = miss to origin, write failure = skip); the sync surface (`SyncCache`) bridges via `block_in_place` and is multi-threaded-runtime only — on current-thread runtimes it always misses — so async-middleware hot paths must use `get_async`/`set_async`/`delete_async`/`contains_async` (no bridge) | fail-open (no switch) | Cache loss only affects hit rate, not correctness; the cache layer has no meaningful fail-close semantics (denying service is not a cache's job). Connection failures at assembly time still fail loud (surfacing configuration errors at startup) |

Real Redis integration test backend resolution: prefers `SDFORGE_TEST_REDIS_URL`; if unset and a `redis-server`
is on PATH, the test spins up a one-off loopback instance (random port, persistence off, terminated at test
end); only when neither exists does it skip explicitly. Run with:
`cargo test --features "ratelimit-dist,cache-l2" --test dist_backends_tests`
(sync-surface cases need a multi-threaded runtime, see the table above).

## 💡 Best Practices

1. **Enable features on demand** — for HTTP only use `--features http`; do not default to `full`: it saves about 46–47% compile time and roughly 60% of library size (see the [compile-time gating benchmarks](VS_SERVER_LESS.md))
2. **Call `init_all_plugins()` at the top of `main`** — otherwise release builds (LTO + dead-code elimination) may strip the inventory registrations
3. **Unify errors with `From<MyError> for ServiceError`** — business errors convert automatically via `?`, with error codes/status codes managed centrally
4. **For security-related deployment practices, follow the security document** — production host, JWT secrets ≥ 32 characters, `ConnectInfo` configuration, explicit API Key seeding and rotation, etc.; see [security document](SECURITY.md#-security-best-practices)
5. **Declare status codes for write operations** — POST creation-style endpoints use `#[forge(status = 201)]` or `ServiceResponse::success_with_status`
6. **Reference the example code** — `examples/src/` is organized by protocol module, and `security/comprehensive.rs` is the reference implementation of a complete security stack

## 🛠️ Troubleshooting

| Symptom | Cause and resolution |
|------|------------|
| Registered routes/tools/commands missing at runtime | `init_all_plugins()` not called, or release LTO stripped the registrations; call it once at the top of `main` |
| Compile error: feature not found | Feature name typo or invalid combination; list them explicitly with `cargo build --features "http,security,cache"`; note `default = []` contains no protocols |
| After enabling `mcp` or `grpc`, compile errors mention `sdforge::http` | Legacy code assumed `grpc` depends on `http`; in current versions protocols are independent — check for outdated feature combinations |
| Service started but unreachable externally | `ServerConfig` binds `127.0.0.1` by default; production must configure the host explicitly |
| Short JWT secrets rejected | Since v0.3.0 `MIN_SECRET_LENGTH=32` is enforced; switch to a strong secret |
| IP rate limiting/banning not working | `ConnectInfo` not configured; since v0.4.4 `X-Forwarded-For` / `X-Real-IP` are not trusted without `ConnectInfo` |
| MCP requests rejected for missing headers | The stateless protocol requires `Mcp-Method` / `Mcp-Name` request headers; missing headers make `parse_mcp_headers` return `McpHeaderError`, and the HTTP 400 response is mapped by the downstream transport adapter layer (the framework does not build that mapping in) |
| gRPC server refuses to start citing authentication | With `security` enabled, `GrpcServerConfig.require_auth` defaults to `true`; configure `auth` (dev environments may set `false` explicitly) |
| Port conflict | Find the occupying process with `lsof -i :3000`, then change ports or kill the process |
| Need to locate performance issues | Compare against the [performance baselines](PERFORMANCE.md) with `cargo bench --bench runtime_bench --features http`; compile-time costs against the [compile-time gating benchmarks](VS_SERVER_LESS.md) |
| Other issues | Consult the [API reference](API_REFERENCE.md) and [architecture document](ARCHITECTURE.md), or ask in [Issues](https://github.com/Kirky-X/sdforge/issues) |
